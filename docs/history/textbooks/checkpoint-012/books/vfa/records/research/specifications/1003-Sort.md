## 3. Recurrence fidelity and standard-operation bridges

The source operation is defined for every list. Sortedness is a premise of
the preservation theorem, not a precondition that restricts execution or the
permutation theorem.

The direct adapter must retain these equations, with left insertion on ties:

```text
insert a []        = [a]
insert a (b :: xs) = if a ≤ b then a :: b :: xs else b :: insert a xs
sort []           = []
sort (a :: xs)    = insert a (sort xs)
```

An economical generalization parameterizes the direct operations by
`r : α → α → Prop` with `[DecidableRel r]`. Natural-number `≤` is the checked
source specialization. Alternatively use the existing decidable-`LE` style
of `sourceMerge`; either choice must recover arbitrary payloads ordered by a
key without imposing an order on the payloads themselves. Do not assume
totality, transitivity, or decidable payload equality merely to define the
operations or prove permutation.

Retain a short direct recursive source adapter and prove:

- direct insert equals `List.orderedInsert r` on every input;
- direct sort equals `List.insertionSort r` on every input;
- key-pulled-back direct sort equals `insertionOn key`;
- the Nat instance implements the source Boolean test `i <=? h` faithfully.

The pinned Mathlib definitions were inspected: `orderedInsert` has exactly
the same nil/cons recurrence, and `insertionSort` is a right fold with
`insertionSort_cons` exposing exactly tail-first sorting then insertion.
The proofs should be short structural induction/unfolding bridges. Equality
of sorted output lists alone is insufficient evidence of recurrence fidelity,
especially for measured observations.

Using Lean's proposition-valued `if` with a proved decision procedure is an
explicit language adaptation of Coq's Boolean branch. The Perm chapter's
reflection results and ordinary `decide` correctness justify this adaptation;
there is no need to recreate `bdestruct` as a tactic. Both branch outcomes
and the equality/tie branch need connected checked uses.

## 4. Specifications and weakest useful assumptions

### Source sortedness and conaled's observation

Use an explicit source adapter to `List.IsChain (· ≤ ·)` for `sorted`:
empty and singleton lists are sorted, and the adjacent cons step has premises
`x ≤ y` and sortedness of `y :: tail`. Record/prove those constructor rules
or their elimination equivalence. If a literal new inductive is preferred,
prove its equivalence to IsChain; do not silently call a different predicate
the source definition. Avoid duplicating list-order theory.

The shared draft already supplies:

- `pairwise_iff_indexed` and `pairwise_iff_boundedIndexed`, requiring no laws
  on the relation;
- `indexed_iff_boundedIndexed` and `boundedIndexed_default_irrelevant`;
- `adjacent_iff_indexed` and `adjacent_iff_boundedIndexed`, requiring
  transitivity for the adjacent-to-all-pairs direction;
- `boundedIndexed_iff_getD`, connecting optional lookup with ordinary
  default-valued lookup;
- the `KeySorted`-shaped indexed bridge, to be stated directly with the actual
  existing `KeySorted` abbreviation at integration.

For a general relation, adjacency does not imply all-pairs ordering without
transitivity. The source's natural-number order supplies it. Totality is
needed for the usual insertion-sortedness proof's false comparison branch;
it is not needed for equivalence of Pairwise and the two index contracts.
The existing Mathlib insertion-sortedness facts require decidable relation,
`Std.Total r`, and `IsTrans α r`; adapt these to the shared draft's `Trans`
argument locally rather than introduce global instance machinery.

### Optional and default-valued indices

Recover the exact source propositions:

```text
sorted' xs:
  ∀ i j a b, i < j → xs[i]? = some a → xs[j]? = some b → a ≤ b

sorted'' xs:
  ∀ i j, i < j → j < xs.length → xs.getD i 0 ≤ xs.getD j 0
```

Explicitly type indices as Nat. In the second proposition, the bound on `j`
and `i < j` imply the bound on `i`; the default is never observed. Retain an
arbitrary-default theorem and a checked out-of-range counterexample showing
why deleting the bound changes the proposition. The option version's `some`
premises must be retained; they are its validity evidence.

The source sorting contract has orientation
`∀ xs, xs.Perm (f xs) ∧ SourceSorted (f xs)`.
The existing conaled contracts use output-to-input permutation, so use
`List.Perm.symm` explicitly. A source-facing abbreviation or theorem is
sufficient; do not invent a parallel public sorting framework. The contract
preserves multiplicities, not just membership, and does not by itself assert
stability of distinguishable equal-key records.

The optional section expressly forbids use of `sorted_sorted'`,
`sorted'_sorted`, `insert_sorted`, and `sort_sorted`. Replacing those by a
path through the generic Pairwise insertion theorem and the equivalent
shared bridges would defeat the same purpose. Ordinary correctness may use
library theorems; the optional indexed derivation must be independently
positional. This is a source obligation that a stronger existing correctness
theorem cannot close.

A concrete small proof plan uses no new framework:

1. Prove indexed sortedness of a tail by shifting both successful indices.
2. Prove `nth_error_insert` by the direct recurrence or the generic membership
   theorem plus a successful old-index witness. This helper is independent
   of any sortedness conversion.
3. Induct on the input list for indexed insertion. In the stopping branch,
   handle comparisons involving the new first element using the branch fact
   and the old indexed comparisons; shift both nonzero indices otherwise.
4. In the recursive branch, distinguish index zero from positive indices.
   For the zero/positive case, `nth_error_insert` identifies the returned
   element as the inserted value or an old-tail value. Use the false-branch
   order fact in the first case and the original list's indexed condition
   in the second. For two positive indices use the induction hypothesis.
5. Prove indexed source-sort correctness by list induction and that direct
   insertion theorem, matching the source's final proof.

Review the actual derivation/dependencies, including automation, for this
restriction. A source-text name test is not mathematical evidence. Optional
proof independence is a method-specific coverage requirement; it is not a
claim that the resulting proposition is logically stronger.

### Actual recursive comparison and construction observations

The source resource audit requires more than copying the word “quadratic.”
Instrument the actual source insert/sort recursion, separately observing
comparison invocations and list-constructor requests/visits. Use ordinary
measured pairs (an additive pair of Nat observations is sufficient). Prove
that discarding the observation gives the source function on every input.
State the independent size/cost specification separately; do not define a
desired polynomial and call it the implementation's cost.

Required useful comparison results:

- Insertion performs at most the input length in comparisons; nil performs
  zero, each visited cons performs one, and the first successful comparison
  stops recursion.
- The source `insert 7 [1,3,4,8,12,14,18]` performs four comparisons in this
  model. A stronger reusable example may append an arbitrary tail after the
  stopping value 8 and prove both output-suffix preservation and unchanged
  comparison count. No sortedness of that arbitrary tail is needed merely
  for this branch/path equation.
- Sorting a length-`n` list has at most `n*(n-1)/2` such comparisons, with
  explicit empty/singleton cases. An equivalent division-free inequality,
  `2 * comparisons ≤ n*(n-1)`, is acceptable.
- A concrete arbitrary-size worst-case family, for example descending
  distinct naturals `(List.range n).reverse`, attains the triangular count.
  Relate the witness to the source recurrence and derived sorted output;
  do not assert that every input has that cost. Ascending or all-equal lists
  stop early and provide meaningful contrasting boundary cases.

This comparison count treats a comparison as one primitive event. It does
not establish constant bit/unary comparison time. If weighted time is stated,
give the comparator-cost hypothesis separately, and connect any unary
comparison realization to its explicit cost model from the cross-cutting
preparation. Do not infer native Lean arithmetic costs from source Coq `nat`.
No new benchmark is mandated by a Sort exercise. If the chapter report
retains a positive empirical speed comparison, supply a scoped reproducible
workload; otherwise retain the source statement as a qualified empirical
observation, not as a locally proved speed claim. Other algorithms' full
resource proofs stay in their own chapter scopes.

### The four-versus-five constructor distinction

The source branch is literally `i :: h :: t`, not a reference to the matched
whole list. In the displayed insertion example, charging each explicit cons
construction gives three reconstructed prefix cells plus two in the stopping
branch: **five** requests. A representation that reuses the matched
`h :: t` node and adds only `i` gives **four** fresh cells. Both have the same
list value. The source's displayed four-cell account presupposes that reuse.

Required accepted treatment:

- Prove the exact unaffected suffix **value** equation, using direct source
  recursion or `List.orderedInsert_eq_take_drop` after the exact bridge.
- Name the construction observation being counted. If showing both the
  literal and suffix-reusing variants, keep them separate and prove their
  value correspondence. Do not silently charge one cell for a literal
  two-cons branch while claiming a literal-constructor cost model.
- Prove unconditional list length increases by one; keep that distinct from
  allocated bytes, retained heap cells, and peak memory.
- Record that garbage-collection eligibility depends on all retained roots,
  and actual reuse/reclamation depends on a heap/evaluation realization.
  `4X`, `(4-3)Y`, and the suggested node word sizes are illustrative runtime
  assumptions. Do not present them as unconditional Lean runtime theorems.

A new heap/GC formalization is not needed to handle this source paragraph
honestly. An explicit conditional construction model plus the value theorem,
the corrected literal count, and a clear unproved-runtime boundary suffice.
If physical sharing itself is claimed, a separate heap-identity realization
proof becomes necessary; List equality is not such a proof.
