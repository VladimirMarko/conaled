# #608 assessment: implementation and use

Recommendation: refine toward a small shared represented-chart construction, retain both native filling APIs, and defer migration until an extraction derives both concrete classifiers with exact recovery. For the bounded Sigma study, a pair of native specializations with full selected-operation recovery is useful evidence now. It does not by itself establish a shared implementation. The strongest reason to retain the current APIs is that they already hide chart and dependent-cast bookkeeping from callers while exposing the exact choices used by existing clients.

## Builder work and caller work

The original `SumFilling.lean:9–66` and Cartesian `CartesianDependentFilling.lean:123–176` implement the same dependent algorithm: fill the first projection, use its actual filling witness to form the second box over `pair p a`, fill that box, and pair the results. Their uniformity proofs both compare the subtype containing the first section and its filling witness before transporting the second operation. This is substantive common proof structure. The witness cannot be replaced by an unrelated endpoint or mere existence proof: it fixes the dependent second box.

The difference a model builder must discharge is visible before that algorithm. Original boxes use `Cofibration` and a fixed false cap. Cartesian boxes use `Subcontext` and an arbitrary `r : Term (interval Δ)`; `graph r` enters `sigmaSnd`, and substitution replaces r by its reindexing. `CartesianDependentFilling.lean:61–121` proves the component-box and reindex laws on those exact data. A common Sigma proof could consume these primitive box decomposition/reassembly laws and derive lawful dependent filling. A record with `sigmaFilling_lawful` or selected Sigma preservation as an input would merely relocate the result.

For admission, `LargeFamilyClassification.lean:69–117` shows an already useful builder interface. `SmallPresentation.Data` supplies small fibers and their equivalences. The implementation conjugates maps, constructs chart isomorphisms, lowers transported fillings, and assembles the code. The routine caller supplies presentation data plus the native lawful filling, without any code-map naturality proof. A shared replacement should preserve this division. Asking every constructor caller for chart coherence would regress the existing interface even if it reduced lines in the classifier implementation.

Cartesian contextual classification does analogous represented evaluation, but its current public endpoint is different: `LocalFamily Γ ≃ (raisedContext Γ ⟶ smallFamilyCodes)`, with Γ at level u. `CartesianSmallFamilyClassification.lean:451–501` obtains the actual record and code round trips. It does not expose the original arbitrary-large-context small-presentation constructor. Consequently, a shared large classifier needs a Cartesian adapter implementing chart lifting/lowering and small presentation transport, not just a namespace replacement. This is a mathematical capability extension that belongs with #605.

## Comparison of approaches

| Approach | Builder obligations | Routine caller and migration consequence |
|---|---|---|
| Retain native implementations | Maintain each represented-chart and box proof against its own cube category | Existing users keep native code, fillers, dependent witnesses and substitution laws. Does not remove duplicated generic proof structure. |
| Shared represented classification | Supply a small cube category, represented contexts and generic points, interval representability and its substitution compatibility, a reindexable chosen local operation, and the actual descent/evaluation construction | Builders may discharge recurring proof structure once. Native wrappers should recover current records and operations so callers still provide a family, its presentation and lawful filler. Exact recovery is the adoption gate. |
| Explicit cross-model bridge | Supply context/family/term and comprehension maps; interval and cap comparisons in the required direction; face/box maps; compatibility with reindexing; primitive selected filling preservation | Consumers can transfer an actual selected construction along a named route. This is additional mathematics, not a consequence of sharing the classifier proof. A broad migration would impose obligations on clients that need only one model. |

The shared classifier should construct code naturality and decoder comparisons from represented evaluation. Its generic field list must not simply ask for a code, decoder inverse, and their round trips under new names. Native `LocalFamily` records already provide those conclusions, so wrapping their equivalences would demonstrate packaging rather than extracted proof reuse.

A useful extraction boundary is plausible because represented evaluation is independent of the particular Sigma algorithm. The more ambitious common filling interface has additional costs: dependent section types, cap and face substitution, and the equations for second-component boxes. These costs reflect actual mathematics as well as Lean representation. I have not measured adapter size or author effort and do not infer that extraction is unprofitable from these costs.

## Contracts that migration must recover

`CartesianSmallFamilyClassification.lean:382–409` preserves filling outputs after the actual decoder isomorphism, for every represented cube, face and variable cap. Its record round trip includes the chosen local filler. The original corresponding record equalities are `LocalFamily.decoded_code` and `code_decoded` in `SmallFamilyGlue.lean`. A result retaining only underlying-family isomorphisms would weaken both APIs.

`Examples/CartesianSmallFamilyClassification.lean:14–27` retains arbitrary global output choices and separates different local filling choices at the code level. Its `finThree_variable_fill` at lines 47–55 explicitly quantifies a box with variable source; `tupleDecoder_selected` at lines 66–69 recovers the global decoder choice. `endpointGlue_record` at lines 89–92 retains a selected operation on a proper face, with `endpoint_not_whole` ruling out the mistaken whole-line condition. These are direct regression targets, although the variable-source example itself supplies no concrete nontrivial box.

Original `LargeConstructors.Result` users must keep the difference between the transported returned constructor filler and `NativeDecode.filling` of the code. The constructor audit records `ChartFamily.path_selected`, `inner_selected`, `outer_selected`, and the distinct `encodedInner_selected` route. A common interface that silently chooses the universal decoder's filler would change these contracts. #607 owns the stronger equality question.

The restricted witness clients have a different strength. `Examples/CartesianWitnessPreservation.lean:42–77` preserves the five-field dependent state package and its generalized arguments; restriction is performed on the selected section before forward Pi comparison. Later square and base-change clients retain whole comparison bodies. They are evidence for bounded witness-preserving routes, not evidence that an arbitrary native De Morgan filler becomes the native Cartesian filler.

The theorem `no_interval_retraction` at lines 13–35 gives an exact obstruction: no natural transformation from the restricted De Morgan represented interval to the Cartesian represented interval can preserve both endpoints. A reversed coordinate would have to become a Cartesian dimension reversing those endpoints, but Cartesian dimensions are constants or variables. This excludes the obvious interval identification needed by an unrestricted direct reuse of boxes. It does not exclude other relations, restricted fragments, or separately constructed selected-operation bridges.

## #570 and Felix

`AdjointSquareTransport.curry`, `curry_paste`, `uncurry_paste`, and `mate_paste` derive exact selected-arrow transport from actual adjunctions and a specified square. Their inputs contain no cubical face, cap, box or filler. They are reusable if a future cubical construction identifies the relevant operation as the transpose of an independently preserved arrow, with the correct endpoints and adjunctions. Neither inspected Sigma filling algorithm is presented that way. Wrapping its final term as a transpose does not remove the obligation to preserve the input filler-dependent arrow.

The #570 report is therefore a useful model for the separation of construction, provider and route. Its generic transport need not be duplicated for a genuine adjoint subproblem. Its predicate specializations' thinness cannot test alternate selected fillers; the cubical study should keep its own operation-sensitive controls.

I inspected Felix's comma objects/morphisms and `MakeLawful` at the pinned revision 6f36d28097db7ea5f5df3263db3e8be08f74e490 in `/tmp/felix-8-source`. Comma morphisms contain an actual commuting-square witness. `LawfulCategoryᶠ` and `LawfulCartesianᶠ` derive laws for the source under homomorphism-induced equivalence and explicit preservation hypotheses. This supports separating operations, preservation and derived laws. It does not supply a cubical classifier or license replacing full selected-filler equality by vertex observations. No upstream cubical capability is claimed here.

## Smallest discriminating next step

First give each model a checked Sigma local-family classifier specialization whose decoder recovery identifies the whole chosen filler. Keep the second family genuinely dependent, and use a Cartesian variable cap plus a proper face. An example should inspect a filled dependent second component, so a constant family or a theorem quantifying an unspecified box is not the only concrete evidence. Reindex by two nonidentity substitutions and check the composite on the retained section and its dependent witness.

Then extract only the common represented evaluation argument, preserving those specializations through native wrappers. Acceptance should show that its code naturality and decoder operation recovery are derived, and that clients do not acquire chart proofs. An exact recovery theorem can allow propositional equalities instead of preserving every current definitional reduction, but the consequences for existing `rfl` clients must be checked.

For any proposed preservation bridge, state endpoints and compose primitive box/filler comparisons before claiming Sigma preservation. If T maps one selected component filling problem to another and U maps the latter to a third, the composed route must use the composed family/section maps and the transported first-section witness when forming its second box. A theorem merely equating final vertex readouts does not test this composition. This is a proposed test, not a supplied composition theorem.
