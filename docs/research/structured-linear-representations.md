# Structured linear maps and sparse realizations

Research assessment, 2026-10-30. Inspected source: `8f0fc0c69201475821e9bd6a22c39e1ac6ede2b9`. This note recommends scope; it introduces no formal claims or measured performance results.

Create a bounded follow-up under [#174](https://github.com/VladimirMarko/conaled/issues/174) for **structured and sparse realizations of linear-map application, with workload-dependent costs**. The data-structure research supports deriving replaceable realizations from client operations and observations. It does not recommend selecting one canonical container or first constructing an exhaustive matrix taxonomy. The current [architecture assessment](data-structure-architecture.md) and [author trials](toolkit-author-effectiveness.md) support local representation laws followed by reuse of shared client arguments. Those trials concern sequence clients, not established matrix-author productivity.

## Existing foundation

[ADR 0009](../adr/0009-linear-matrices.md) chooses finite coordinates over a commutative semiring. [`MatrixBackend.representation`](../../Applications/Linear/Matrix.lean) decodes through `Matrix.toLin'`; its inverse and operation squares establish coordinates as representations of linear maps. [`MatrixCompiler.Maps`](../../Applications/Linear/Maps.lean) already composes action interpretations and transports product laws. Preserve this semiring generality, including timing applications; stronger scalar hypotheses belong only on operations that need them.

Mathlib's pinned [`Matrix`](https://github.com/leanprover-community/mathlib4/blob/56a005855ea17e0b0958f73ec801ae140b0a1679/Mathlib/LinearAlgebra/Matrix/Defs.lean) is `m → n → R`. Thus the existing coordinate backend is not itself a verified dense-array storage format. `Matrix.ofArray` and its round-trip law provide a row-major adapter starting point. Comparing sparse runtime work requires an actual instrumented dense implementation or an explicitly stated abstract dense algorithm.

Specialized maps already exist: [`Applications/Linear/Similitude.lean`](../../Applications/Linear/Similitude.lean) supplies certified positive similitudes, `decodeEquiv`, `linearCompositionSquare`, application and change-of-basis contracts. Its certified carrier deliberately exposes no addition operation. Mathlib already has [`Matrix.diagonal_toLin'`](https://github.com/leanprover-community/mathlib4/blob/56a005855ea17e0b0958f73ec801ae140b0a1679/Mathlib/LinearAlgebra/Matrix/Diagonal.lean) and [`Equiv.Perm.permMatrix`](https://github.com/leanprover-community/mathlib4/blob/56a005855ea17e0b0958f73ec801ae140b0a1679/Mathlib/LinearAlgebra/Matrix/Permutation.lean). New work should add useful realizations and connected clients, reusing these semantics.

The matrix optimization example is also implemented. [`Examples/Optimization.lean`](../../Examples/Optimization.lean) proves semantic equivalence and restricted optimality for two matrix-chain parenthesizations. Its checked dimensions give work costs 400/550 and intermediate storage 40/25. These are stated formulas, not instrumented sparse kernels or complete memory costs. The older [optimization research](compositional-optimization.md) describes the original proposal; the current example supersedes its unimplemented status.

## Separate structure, coordinates, storage and execution

A mathematical restriction, such as preserving a form, belongs in a predicate or certified carrier with exactly the operations whose closure is proved. A diagonal description, a permutation, a block decomposition or a low-rank factorization is data from which a map can be realized. Sparse support is relative to chosen coordinates; changing basis can remove sparsity. CSR, COO and dense buffers are storage choices, while traversal, accumulation and conversion are algorithms. These distinctions are proposed design guidance consistent with the existing coordinate and similitude interfaces, not a new mandatory class hierarchy.

Use a diagram of ordinary decoders: specialized representation → coordinate matrix → linear map. Reuse `Squares.Rep`, composition and operation squares; use a validity subtype or `Relational.RelRep` when raw formats have invariants. Duplicate coordinates, alternative factorizations and explicit stored zeros can give different representations with the same matrix, so decoder injectivity must not be presumed. Requiring every specialized kind to support every matrix operation would also be wrong: closure must be established for each operation and result representation.

The source survey's ADT principle has a direct primary precedent: [Appel's ADT chapter](https://softwarefoundations.cis.upenn.edu/vfa-current/ADT.html) separates specifications from hidden representation invariants. For sparse formats, [Chou, Kjolstad and Amarasinghe](https://arxiv.org/abs/1804.10112) describe formats by capabilities and properties, with implementations composing into CSR, COO and other layouts. This is evidence for a design method; it supplies no Lean proof or global optimality guarantee here.

## A bounded first issue

Use one immutable, finite matrix applied repeatedly to vectors over exact scalars. Implement a compact diagonal realization as the structural specialization and one sparse realization alongside an explicit dense baseline. A coordinate-entry sequence with specified additive duplicate semantics is a reasonable first sparse representation: it avoids prematurely making compressed-row invariants the public interface. Assess CSR as the next adapter when repeated row traversal justifies conversion. [SciPy's CSR documentation](https://docs.scipy.org/doc/scipy/reference/generated/scipy.sparse.csr_matrix.html) distinguishes stored values, including explicit zeros, from canonical sorted/no-duplicate form; it also identifies efficient matrix-vector products and expensive changes to sparsity structure. Those implementation tradeoffs do not imply a universal preferred format.

Suggested acceptance, to be owned by the issue:

1. Define independent matrix-vector meaning, coordinate choices, validity and permitted observations. Prove each implementation's application square and at least one two-stage application composition through existing linear-map/matrix laws. Preserve the current backend contracts.
2. Use existing Mathlib diagonal/permutation semantics where relevant; make diagonal application a checked specialization rather than a disconnected new taxonomy. State which operations preserve each chosen structure and which produce a general result.
3. Instrument actual loops and prove erasure plus resource equations. Count stored entries rather than silently replacing them by mathematical nonzero count. Charge dense output initialization/materialization, input access, scalar work, index traversal, construction and conversions. If converting from an arbitrary coordinate function, include the scan required to discover entries. Equality with zero is an extra assumption for zero-eliminating construction, not for every representation.
4. Compare single and repeated applications, include a conversion that fails to repay its cost, and show a tariff/workload reversal or tie. Include empty shapes, a zero matrix, explicit zeros, duplicate cancellation over a suitable ring, and an invalid raw representation when invariants are used. Keep retained space and peak workspace separate from additive work.
5. Instantiate existing optimization contracts with explicit feasible representations, target capabilities and the whole workload. Include an unavailable candidate and a least-cost versus Pareto distinction. Prove a connected client once and recover all accepted implementations from local laws. Use statement review, checked examples and repository build/audit/review requirements.

## Compositional optimization and ownership

[`Optimization.Basic`](../../Applications/Optimization/Basic.lean) already supplies `minimizers`, `pareto`, attainment, objective pullback and workload maps. [`Transport`](../../Applications/Optimization/Transport.lean) requires cost agreement and monotonicity for image optimality, with dominating target lifts for target-wide optimality. Semantic equality alone supplies none of these. `select` is noncomputable; an executable selector is a separate deliverable.

Candidate boundaries must retain format and conversion requirements. A locally cheap producer can lose after conversion to its consumer's required representation. Sparse multiplication can also change support. For later plan search, reuse [`Optimization.Thinning`](../../Applications/Optimization/Thinning.lean); prove dominance adequate for the admitted contexts before pruning. [`ScanSearch`](../../Applications/Parallel/ScanSearch.lean), accepted under #243, is a concrete precedent using continuation profiles and residual budgets, not a matrix pruning theorem to assume by analogy.

Consume completed #185 ordered-summary laws, #239 measured bounded-realization methodology and #249 author-trial findings rather than reopening them. [The #239 implementation record](bounded-summary-implementation.md) demonstrates actual measured operations, charged construction/conversion, restricted candidates and incomparable work/storage objectives. Earlier assessment statements calling #185 open are historical. #235 remains the owner for demonstrated preservation-interface mismatches. The new issue should not depend on finger-tree implementation or duplicate generic optimization foundations.

Defer a complete format catalog, automatic sparse matrix multiplication planning, floating-point reassociation/error analysis, physical CPU/GPU performance and a universal optimizer. The first issue can establish compositional semantic and resource contracts without claiming that every sparse representation is faster or that the matrix plan class is globally optimal.
