# Prepared lowest-common-ancestor queries

The modules under `Applications/Sequences/LCA/` construct static LCA queries
through Euler tours, range minima, sparse tables and shared block tables.
They separate independent tree semantics from the representation and its
modeled resource bounds. The prepared-query interface is described in
[Prepared queries and phase requirements](prepared-query-contracts.md).

## Semantics and representation

`Tree` admits arbitrary finite branching. Nodes have path semantics and dense
numeric identities. Ancestry and the unique lowest common ancestor are defined
before the Euler representation. An empty tree supplies no node-query domain;
the represented trees are nonempty. A query may arrive after preparation and
may repeat an earlier query.

The Euler construction produces `2*n-1` visits. Its finite first-occurrence map
translates two dense node identifiers to an inclusive interval of the depth
sequence. Adjacent depths differ by one. Every minimum of that interval visits
the same LCA node; the RMQ implementation consistently chooses the leftmost
minimum. Recovery reads the node identity at the returned tour position.
`TreeReduction` composes this proof with a backend RMQ law through
`Resources.Prepared.Reduction`.

The macro sparse table uses two overlapping power-of-two intervals. The proof
uses minimum's idempotence as well as associativity; a checked addition example
rejects that overlap rule. Level selection reads a prepared floor-log table.
Rows are constructed from earlier stored rows, with their spans obtained by
doubling.

The block width is `max 1 (floor(log2 m) / 2)`, where `m` is the number of depth
entries. A width-`b` block has `b-1` signs and at most `2^(b-1)` classes.
`BlockShape` proves that equal sign patterns preserve relative heights up to an
additive offset. `Micro` transfers the exact leftmost argmin observation through
that classification. Shared tables retain relative answer indices, discarding
absolute depth offsets. Each class table is generated by cumulative minima,
not a fresh scan for every interval.

`BlockedRMQ` reconstructs answers for queries wholly inside one block, adjacent
blocks, and blocks separated by a nonempty macro interval. Upward padding
completes a final short block. Admitted endpoints remain in the original input,
and the padding proof transfers their answers back to its independent RMQ
specification. Absolute depth/index keys preserve leftmost ties across blocks.

## Execution model

The measured programs use finite initialized vectors as stores. Indexed reads,
writes, comparisons, word arithmetic and loop control have explicit tariffs.
A vector update denotes a write into reserved target storage. It is not a
claim about persistent array copying in generated Lean code. Preparation builds
the shared tables, block classifications, macro rows and logarithm table from
these operations. Value/erasure theorems connect their outputs to the semantic
construction; work bounds follow their executed recurrences.

`TreeBackend`, `TreeEmission` and `TreeMaps` count caching subtree sizes,
emitting the tour, initializing maps, and scanning first occurrences. Runtime
dimensions are obtained from the measured cached count. The query path takes
dense identifiers, so no uncharged tree search or expected-time dictionary
lookup occurs during operation.

The bounded RMQ input includes a proof that depths and node identities fit its
length bound. The tree conversion discharges those conditions. The adjacent
±1 condition alone would allow arbitrarily large absolute depths and would
not establish a finite word-width requirement.

`WordKey` encodes a depth/index key as `(depth+offset)*stride+index` after
establishing nonnegative shifted depths and indices below the stride.
`WordKeyStorage` proves exact identity and order preservation, minimum
transport, finite-store read/write simulation, and bounds on the packing
intermediates. These lemmas require the caller's depth and index bounds; they
do not assume arbitrary integers fit into words.

## Phase tradeoffs

The backend is specialized to a fixed input length `m`. Its block dimensions
and logarithms are configuration shared by inputs of that size. The proofs do
not certify a uniform runtime compiler that chooses those parameters for an
unknown input size.

The three implementations answer the same total RMQ specification. Invalid
intervals return zero; valid intervals return a leftmost minimum index.
`Catalog` supplies direct scanning, `SparseCatalog` adapts the full sparse
executor, and `Backend` supplies shared-block queries. Their work budgets are:

| Strategy | Preparation operations | Worst-case query operations |
|---|---:|---:|
| Direct | 0, transferring ownership of the input | `10*m+13` |
| Sparse | `26*m+3+floor(log2 m)*(11*m+7)` | 16 |
| Shared blocks | `1024*m` | 57 |

These are proved upper bounds with conservative constants. They are not
measurements or claims that the shared strategy always performs fewer primitive
operations than the sparse strategy. The shared construction improves the
asymptotic preparation and storage requirements while preserving a constant
query bound. The LCA reduction additionally charges map construction and every
query translation/recovery operation.

`BackendBounds` combines those operation counts with the allocation and
control interpreters. Shared queries retain at most `36*m` words; the complete
preparation/query peak budget is conservatively `512*m` words. `Workspace`
retains every buffer allocation, including seed rows and canonical-height
temporaries. `Control` follows the preparation's saved scalar frames, and
`QueryStorage` retains the query's produced scalar values and bounds each
prefix. `Storage` observes the actual nested arrays, while `PackedBackend`
places their finite-word representations and descriptors into a finite arena.

`MachineCapacity` separates address and packed-key width from the memory
budget. `BackendBounds.Machine` requires the actual preparation and query peaks
to fit the capacity and derives the arena eligibility used by the packed
representation. A finite width exists for every admitted input at capacity
`512*m`. The width bound covers arithmetic intermediates as well as stored
keys; its quadratic key envelope is `(4*m+4)^2`.

For a tree of size `n`, put `m=2*n-1`. `TreeReduction` composes the RMQ contract
with map construction and query translation. The real-time requirement allows
unbounded startup, admits 62 modeled operations per response, reserves
`n+38*m` retained words, and bounds peak space by `n+516*m+8`. Preparation still
terminates and has its own linear operation bound. Unsupported tree changes
require preparation again; a zero maintenance profile supplies no update
operation.

`StrategySelection` filters direct, sparse and shared candidates by startup,
query, retained-space and peak-space requirements, then minimizes preparation
work among feasible candidates. Its agreement and deadline results consume
each selected implementation's `Laws` and `Bounds`. Minimality is relative to
that three-element catalog. These constructions demonstrate reusable
certification and finite selection; they do not automatically discover the
Euler reduction or invent shape sharing from an arbitrary program.

## Provenance

The motivating presentation is SithDev's
[LCA: How to Solve an Impossible Problem (with Data Structures)](https://www.youtube.com/watch?v=IePrsH3gU_A).
Its metadata and English automatic captions were inspected with `yt-dlp`.
The formal specification fixes the inclusive endpoints, tie policy, small-input
fallback and finite-capacity conditions independently of the narration.

The construction follows Michael A. Bender and Martín Farach-Colton,
[The LCA Problem Revisited](https://cadmo.ethz.ch/education/lectures/HS18/SAADS/papers/lca.pdf),
LATIN 2000, LNCS 1776, pp. 88–94
([DOI](https://doi.org/10.1007/10719839_9)). Its Lemma 1 separates the Euler
conversion's preparation and query overhead; Sections 3–4 give sparse tables
and shared relative block patterns. This is their simplified construction,
not a formalization of the original Harel–Tarjan algorithm. The
[MIT 6.851 static-tree lecture notes](https://courses.csail.mit.edu/6.851/spring21/scribe/lec15.pdf)
provide a supporting account of the word-RAM assumptions and indirection.

The finite-store programs, exact tie contracts, storage schedules and
prepared-query composition are this repository's implementation obligations.
The references do not establish their correctness. Nor do the Lean proofs
certify compilation to a physical machine, native allocation behavior,
scheduling, interference, or wall-clock worst-case execution time. Dynamic
updates and known-batch offline LCA are outside this immutable preparation
contract.
