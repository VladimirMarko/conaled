# #625 implementation and use assessment

Recommendation: build the constructor interpretation over the universal decoder first, in both models, then derive the total SIP. Do not make a presented-discrete universe the primary route. Its admission, preservation under Glue, and univalence restriction would be additional mathematical work, whereas the raw constructor family already has the needed native ingredients.

This is a source inspection, not a checked prototype. Existing declarations below were inspected; proposed declarations and proof plans remain unverified in Lean.

## Existing implementation constraints

`Presheaf.StructureIdentity.family` uses `familyFromPresentation` and the supplied global `j : A ≅ constantFamily Γ S`. It cannot range over the universal decoder by dropping this parameter: `Transport.map` accepts equivalences, while arbitrary family restriction maps are not equivalences. Moreover, `Description.Data (.function D E) (A.obj x)` is an ordinary function space, whereas native `pi` at `x` is `PiElement`, with values at all restrictions and naturality. The latter is the appropriate interpretation for the universe family. Comparing these implementations is a real proof obligation.

`LargeFamilyConstructors.lean` already gives presheaf small presentations for sigma, pi and path, and `LargeConstructors.Result` bundles a small code, native decoding isomorphism and lawful filling. `SmallPresentation.Data.pi` establishes smallness through represented restrictions, avoiding an unjustified assumption that the large base is small. `NativeDecode.filling` supplies the universal carrier's filler. Sigma, Pi, and path fillings are already lawful.

Cartesian `sigmaFilling`, `piFilling`, and their lawful proofs work at arbitrary same-universe contexts. Thus a lawful Cartesian semantic family over its own carrier universe need not wait for all of #605. Its classification back into the *fixed small* universe at a larger context does require the missing small-presentation/classification constructor route. Distinguish native admission as a `Family` with lawful `Filling` from fixed-level small code admission; #625 needs an honest account of both.

Both models already prove their own `Presheaf.SmallUniverse.NativeUnivalence.univalence` and `Cartesian.SmallUniverse.NativeUnivalence.univalence`. `NativeUnivalenceTotals` and Cartesian completion use a based path singleton, equivalence total contraction, and `HomotopyEquivalence.ofContractibleTotals`. Those proofs establish reusable ingredients, but do not themselves provide SIP for arbitrary structures.

## Declaration-level route

1. Define `Description.nativeFamily (D) (A : Family Γ) : Family Γ` by recursion: carrier is A; fixed T is the constant family (lift T as required); product is `sigma` with the second factor pulled back along the first projection; function is `pi` with the same pullback. Define `nativeFilling D F hF` and its lawful theorem by the same recursion. Prove substitution comparisons using existing Sigma/Pi reindex interfaces, rather than assuming definitional equality for Pi. Then specialize A to `liftedDecode (𝟙 smallFamilyCodes)` in the presheaf model and the Cartesian universal decoded family in its model.
2. Supply `nativePresentation` in the presheaf model recursively using `SmallPresentation.Data.sigma/pi`. Fixed T needs an explicit small type at the chosen level; carrier uses `decodePresentation`. The corresponding Cartesian presentation and classification bridge is the precise #605 dependency, not Cartesian Pi filling itself.
3. Define native expression interpretation as terms/maps in this family. Establish compatibility with reindexing and application. Interpret laws with native paths and native dependent Pi/Sigma. Equality laws become proposition-valued only when their compared types are internally sets. Make that requirement visible. Implication and universal quantification preserve propositionhood under the required native principles. Do not translate native equality to Lean equality at each generalized element.
4. Use a native `Structured := sigma (Universe.family Γ) structuresOverGenericCarrier`. Construct its lawful filler from the universe and structure filler. Prove an internal Sigma-path decomposition, preserving the carrier path and dependent structure path. I did not find an exported general Sigma-path decomposition; the `CartesianWitnesses.sigmaPathIso` is a restriction comparison for Sigma-of-path and is not that theorem.
5. Define native field preservation independently by recursion on D, starting from the supplied native carrier equivalence. Prove that dependent paths over the selected ua line correspond to that relation. Function fields require native function extensionality/application reasoning, not Lean `funext` on `PiElement` observations. Compose with the model's own univalence and the Sigma decomposition to obtain the total structured path/isomorphism equivalence. A fallback definition of preservation as transport along `equivToPath` may be useful internally, but only fieldwise comparison makes it a usable SIP.
6. For law-bearing structures use the proposition-family extension theorem: the law witness contributes no additional identification once underlying data preservation holds. For genuinely dependent data retain the dependent path field; do not apply this erasure to arbitrary witnesses.

## Minimal requirements and recovery

Raw carrier/fixed/product/function data do not need sethood to form native families. Law fields require it only where equality is intended to be propositional. A set-carrier fragment is sufficient to recover the current monoid/lattice examples, but its admission and univalence are separate obligations if packaged as a universe. Keeping hypotheses on carriers and equality target types is a smaller initial implementation requirement than constructing that subuniverse.

`.fixed Prop` currently means the *constant host set of propositions*, not an internal universe of propositions. It may remain a legitimate fixed discrete field when recovering `Examples.CompositionalStructureIdentity.relation` and `state`; document this semantics. Substituting an internal proposition universe would change the client contract and needs an explicit comparison.

Prove a constructor-recursive comparison `nativeFamily D (constantFamily Γ X) ≅ constantFamily Γ (D.Data X)` and extend it along an explicit presented carrier. This exposes the required Pi comparison once, and recovers `Description.preserves_iff`, `Specification.preserves_iff`, `stateModelEquiv`, and `state_transport` through the new native result. Prove laws for native transport of expressions and solution families, so `Formula.solutionEquiv` and the chosen `falseIdempotent` survive as dependent clients. Check Bool complement for monoid/order/lattice and the existing noncommuting Fin 3 swaps for composition order; include inverse recovery.

A complete cross-model result requires comparison of native structure families, carrier equivalence witnesses, and native univalence maps. Existing `Cartesian.StructureIdentity.restrictionEquiv` only compares presented fixed-equivalence paths. Restriction comparison of Pi is particularly substantive because the cube sites differ; a blanket equality should not be inferred. State any remaining Pi/path/univalence comparison as an exact residual boundary, while establishing each model's SIP independently.

The first useful implementation slice is the native constructor family, lawful filling, smallness evidence where available, and constant-family comparison with a binary-operation client. It removes the global presentation requirement from family formation and creates reusable code for the total theorem. It does not complete #625. The next dependencies are native law interpretation with sethood, Sigma-path decomposition, native field-preservation comparison, and the total theorem with both-model recovery.

## Cartesian fixed-level classification follow-up

The presheaf classifier port is supported by concrete Cartesian APIs: `SmallUniverse.liftedDecode`, `SmallUniverse.raisedIntervalIso`, `SmallUniverse.NativeDecode.filling/filling_lawful`, and `Cartesian.Raising.lowerElements/family/raiseTerm/lowerTerm/totalIso/lowerMap` in `CartesianUniverseComposition.lean`. The existing `LocalFamily.code` and `decodeCodeIso` in `CartesianSmallFamilyClassification.lean` classify families on raised small contexts. Porting `SmallPresentation.Data` and `LowerFilling` provides the missing large-base fixed-level classifier. `LowerFilling` must raise both the face and the variable cap term in a Cartesian open box. The chart utilities needed for code naturality already exist in `CartesianUnivalence.lean` (`chart`, `chart_restrict`, `chart_generic`, lines 556 onward); extracting them below univalence would avoid an unnecessary dependency if desired. I have not checked this port in Lean, but no new mathematical principle appears necessary for this dependency.
