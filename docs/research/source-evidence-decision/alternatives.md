# Independent alternatives assessment for #699

Recommendation: select the bounded semantic contract for both a native correspondence route and a separately proved finite certificate route. Keep their evidence interfaces distinct. Sequence implementation around one shared source semantics and one shared conclusion, with native correspondence first if that is the chosen engineering order. Do not describe that order as a decision that native Lean judgments are the general programmer contract. Symbolic normalization is a viable complement on these exact examples; it can initially produce native proofs or finite certificates without creating another mandatory public format. Defer MMT publication and a common extensible proof language until a named consumer needs their additional capabilities. This is a recommendation for the owner, not adoption.

The shared obligation should name the original source, exact dependency closure, parameter values, input predicate, primitive semantics, selected encoder and decoder, artifact semantics and the artifact actually consumed. For the pure client it concludes equality of both components of `D3(q)`, for every canonical input `0 ≤ q < 16`. This comparison does not exclude the last three alternatives because they lack an adapter. Symbolic checking already meets the algebraic requirement on the two clients, conditional on its unproved checker laws. Theory indexing addresses reusable meanings and interpretation composition. A common proof language addresses shared derivation authoring and interchange. The missing requirement for selecting either larger framework now is a concrete consumer whose necessary reusable proof or heterogeneous interpretation cannot be adequately served by the bounded routes. The current clients provide no such discriminator. Their absence is a prioritization reason, not a claim that those frameworks cannot support the examples.

Native and finite evidence are also not disjoint foundations. A theorem prover can generate a table, and Lean can prove the finite checker's acceptance theorem. Their relevant difference is what a caller supplies and what the checker verifies. Requiring every finite producer to supply the semantic result as a native record would erase the proposed alternative. Requiring a native declaration-to-AST correspondence when the original source is native Lean does not erase it: finite data can still establish the optimization and artifact correspondence independently.

Concrete concerns and minimum corrections:

1. **Existing precedent does not already provide the arithmetic bridge.** `GraphTranslationValidator.check` (`SquareKit/Internal/GraphTranslationValidator.lean:34`) checks version, environment, theorem identity, expected type and body against its bounded graph source. `check_sound` at line 77 derives source-associated typing and denotation. This supports the discipline of inspecting actual objects, but its graph language and approved primitive environment do not implement integer/residue admission. `RegionalAdmission.Realization` at line 40 is a `Plan Input Bool` with an example-specific observation, not the desired generic integer relation record. The smallest correction is to cite those results for their particular reusable obligations and use `run_related` directly for the new state relation.

2. **The finite checker must certify the advertised domain.** The old `finite` routine (`experiments/compiler-evidence/probe.py:171–186`) checks submitted rows, initialization, decoder agreement, closure and output equality. This suffices for executions beginning at the checked initialization. It does not generically certify every possible decoder input or every pair in a separately advertised relation. For this machine, input `d=1` and closure from `q=0` force all 16 canonical target states, so the gap can be discharged. The simpler explicit production obligation is coverage of the selected graph `{(q,3*q mod16,q) | q<16}`, plus the separate full pure table. Do not silently generalize reachable closure to total correspondence on another machine.

3. **Do not infer integer facts from residue equality.** Source inspection confirms that the probe evaluates exact nonnegative expressions before final remainder (`evaluate`, `source_step`, lines 48–86), while its bit arithmetic is a separate lowering experiment. The first interpretation sends both 0 and 16 to the same residue. It cannot reflect arbitrary integer equality, inequalities or exact intermediates. Preserve bounds in the integer context; prove modular bit operations realize residues separately. The six-bit temporary bound of the old diagnostic is not a theorem that four-bit exact arithmetic is valid. The smallest correction is to state the arithmetic interpretation as part of each accepted artifact and give the new modular realization its own law.

4. **A native-only implementation milestone needs an explicit capability label.** It may reasonably be the first implementation step because the local compiler laws already exist. It must not report the finite route as delivered or make all external sources accept native Lean judgments. Conversely, two routes need not duplicate a maximal universal record: share the concrete semantic conclusions and trace theorem, and let the evidence formats expose their own checking obligations.

5. **The symbolic route has a genuine completeness distinction, not a fragment mismatch.** As a paper separator within the named arithmetic syntax, `8*q*q mod16` and `8*q mod16` agree for every integer `q`, since `q*(q-1)` is even, but their formal polynomial coefficient maps differ. Finite evaluation can establish this equality; coefficient normalization alone rejects that certificate. This is a useful retained discriminator if symbolic normalization becomes a public route. It does not weaken its valid argument for `D3` and the selected transition. No new executable check or Lean theorem of this separator was run here.

For composition, each route must deliver the same equations. Let `F` send integer expressions interpreted modulo 16 to ring terms, and `G` send residues to little-endian four-bit representations. Require evaluation preservation for `F`, residue-operation realization for `G`, and compatibility with simultaneous substitution, including product and let structure. Then direct/composed agreement follows by composing those equalities, and applying the result to both components of `D3` retains the chosen decoder. `SquareKit/FirstOrderSubstitution.lean:78` already supplies the typed term evaluation/substitution law for a fixed primitive meaning; the cross-interpretation primitive and representation laws remain to be supplied. The completed reports give a paper argument and 1,280 diagnostic comparisons, not a checked universal arithmetic composition theorem. No route may recover lost integer distinctions by claiming reflection from the quotient.

Existing target code reduces the new work for the two selected clients. `Applications/Circuits/Words.lean:17–44` defines little-endian word representations and proves both round trips; `add` and `add_correct` at lines 133–141 cover every width, including four. `Applications/Circuits/Execution.lean:19–29` relates the circuit evaluator to its digital meaning. Two additions can implement multiplication by the fixed coefficient 3, after proving the relevant source rewrite and residue connection. These inspected results do not establish lowering of arbitrary variable multiplication in the whole proposed fragment. A production implementation claiming that whole fragment must supply that primitive lowering and law, or clearly report a narrower delivered target capability while retaining the agreed source/evidence contract. The gap is shared by all evidence routes; MMT publication or a different proof format cannot substitute for the missing target operation law.

Host independence follows from keeping these meanings, observations, association checks and accepted evidence capabilities stable. A Rust or OCaml compiler can still ask Lean to verify the native proof and can produce finite certificates for an independently proved checker. Reimplementing the checker requires justification of the new executable checker against its specification or continued use of the existing trusted checker. Changing the verification foundation is a separate interpretation problem. No caller should need to rewrite a mathematical proof merely because the candidate producer changes host language. Artifact serialization, verifier invocation and the exact object eventually executed remain part of the trust account.

The smallest useful next implementation discriminator is one end-to-end, source-bound finite acceptance theorem for these clients, exercised alongside native correspondence on the same source, selected decoder and artifact. It must include the pure table, state closure, changed syntax and the stale/freshly rebound wrong-program failures. That demonstrates a genuinely distinct producer interface while reusing the same semantic result. It should not wait for a general Lean quotation facility or an MMT importer. The owner's contract choice itself is decidable from the present bounded evidence; broader author-productivity rankings are not.
