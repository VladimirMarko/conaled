# #533 alternatives and generality assessment

Recommend a direct executable adapter as the implementation baseline, with composition and reversal supplied as ordinary measured programs. Keep a finite transport-expression interpreter as an optional comparison, justified by a concrete inspection or normalization workload. Do not make that interpreter a prerequisite for Boolean negation, finite permutations, or the complete state package. A broader evaluator remains a legitimate future design, but none of the frozen observations requires it.

This recommendation retains every acceptance item, including actual decoded native endpoints, proof-bearing package behavior and full workload costs. It does not recommend replacing the package with a carrier-only example.

## Comparing the candidates on the same workload

| Candidate | Capability retained or added | Obligations and cost consequences |
|---|---|---|
| Supplied executable maps and operations | All frozen value and package observations; forward, reverse and sequential changes; direct clients | Supply both map implementations and erasure laws. Charge each actual call and setup. Derive workload simulation through the native comparison theorems. No syntactic admission or normalization theorem is needed. |
| Finite identity/composition/inverse syntax | Reified recipes that can be inspected, serialized in a separately specified format, normalized or compiled once | Typed endpoints and primitive realization contracts; interpreter termination by structural recursion; native denotation correctness; normalization correctness for the observations; cost of visiting nodes and producing/retaining the normalized result. Serialization correctness is additional, not automatic. |
| Broader evaluator | Could admit dynamically supplied source terms, dependent transport programs, demanded computations or explicit heap sharing beyond fixed recipes | Must specify the extra source fragment, operational rules, executable primitives and observations. Needs progress/return or bounded execution evidence as applicable, simulation into actual native semantics, and a resource interpretation. A semantic ua theorem supplies none of these operational obligations. |

The first two can share primitive measured implementations and a common native correctness target. Syntax should compile to the direct interface, so choosing syntax need not remove native callers. Conversely, replacing a sequence of closures by a composed closure is not by itself a proof that fewer conversions execute.

`Applications/Languages/ParserWorkload.lean:56–74,128–146,261–327` is a real syntax consumer: map syntax includes identity, complement, composition and prefix shift; derivative processing creates shifts and transport layers; `Map.run_result` identifies the executed map; setup/query code measures four policies. Its normalization is useful because the consumer repeatedly restructures and traverses that representation. This is positive evidence for syntax where such structure exists. It does not establish that a frozen finite permutation client needs another language. In particular, `Spine.pack` collects maps into composition; do not describe it as an existing inverse-cancellation normalizer.

There is another viable formulation beyond those local precedents: tabulate a supplied finite bijection into explicit forward/backward tables, optionally tabulate its conjugated operation, then execute table lookups. This permits preparation and repeated-use experiments without interpreting cubical syntax. It preserves arbitrary finite permutations if the tables are checked against the supplied maps and their inverse laws. It needs table-construction, lookup, storage and rebuild costs. A tiny domain may make the overhead unattractive; that is an empirical/model comparison, not a reason to rule out the formulation. Do not quotient the semantic input to a bare permutation when the claim retains the original chosen native path or contraction witness. Keep the original native endpoint in the correctness theorem even if the executable table ignores proof data.

## Complete costs and retention

Use `Resources.Measured.bind` and `Resources.run`, especially `Workload.lean`'s `run_cons`, `run_append` and `run_value_fusion`. The runner should retain actual intermediate states, not just multiply a guessed operation price. For a target state `b`, the direct conjugated step executes:

```
a := backward b
na := sourceStep a
nb := forward na
```

Its declared work is the sum of those three executions at those inputs. A target observation adds the actual observer cost; an observation defined by pulling a source observer back adds its own backward conversion. Initialization includes forward conversion of the initial state and any setup actually performed. Final conversion is charged if the contract returns a source-coordinate state. Specify which coordinates outputs use so conversion is neither omitted nor charged for an operation that does not run.

For a workload of length k, compare the same operation/observation sequence and endpoints. Show k = 0, k = 1 and repeated use. Zero use still incurs eager setup if the selected API performs it. A lazy API that avoids setup is a different policy and needs its own behavior. A repeated state-machine workload generally has changing states; the exact sum must follow those states even when a bound eventually simplifies to k times a uniform tariff.

A useful optimized comparison is to retain the source-coordinate state throughout a batch, execute source steps there, and convert at each demanded target observation or final export. This can remove round trips between successive steps. Its simulation invariant is `b = e a`, and its observation schedule must match the baseline exactly. It needs no transport syntax. This is a proposed optimization, not a supplied theorem. If the client permits external target-state replacement, that update requires conversion or invalidation; otherwise scope the session to an immutable representation choice and explicit restart/rebuild. Count both retained representations if both survive.

`Prepared.lean:17–87` provides preparation/query semantics, storage bounds and explicit maintenance. Its `answer : R → Q → Measured A Nat` does not update R, so do not force a changing machine state into immutable prepared-query semantics. Use `Workload.run` for state transitions; use `Prepared` for a static conversion table or other immutable prepared part. Its maintenance record provides a real update law and cost; a zero maintenance profile alone provides no update operation.

Normalization can lawfully cancel inverse conversions in the *output program* if its correctness proof preserves the selected observations. It must still charge normalization/setup and any remaining dispatch or observation. The unnormalized program's inverse law does not remove its executed work. Reuse the existing padding rejection and short-workload controls identified in `docs/research/representation-transport-costs.md`, rather than creating another generic counterexample framework.

## Imported book reuse with actual hypotheses

`Applications/Resources/SharedDemand.lean` supplies a useful FDSA-derived option-cache model. `Valid`, `request_value`, `run_replicate_empty` and `step_preserves_cached` assume a fixed pure callback per identity and no overwrite of retained results. Its header explicitly charges only callback work: lookup, update and request administration are zero in that observation. Reuse its semantic and callback-count laws if caching a fixed map/input pair. They do not establish complete #533 costs. Caching a transition merely by operation name is invalid when its input state changes; the identity must include the relevant input and representation version, or updates must invalidate entries.

`Applications/Memoization/Slots.lean:10–19,39–83` is a more concrete finite-storage candidate: reads cost `i.val + 1`, writes have a stated traversal cost, and setup costs n. Thus finite tables need not be assigned fictional constant lookup costs. Adapting tabulation still requires measuring the work to compute entries; `tabulate` alone does not account for supplied map evaluation.

The PFDS-derived machine offers deeper sharing evidence but is not a free adapter. `Applications/Suspensions/CacheAccounting.lean`, `cacheWrites_observe_le_one`, requires bounded configurations, distinct pending memoize addresses and `FreshEntries`; the source specialization in `Pure/CacheCounts.lean` discharges these under represented memory/captures, an immutable world, hereditary pure code, compatible primitives and an actual finite evaluation witness (`docs/research/pfds-cache-counts.md`). These results concern successful writes and actual event traces, not arbitrary host closures or complete time/space bounds. Use them if #533 chooses that machine as its computation model and proves the embedding. No frozen client currently needs reentrant suspensions or exceptions, so that migration would add obligations without an identified extra observation.

## Discriminating test and unresolved risks

Before selecting normalization, implement a matched comparison specification using a noninvolution `c = swap01.trans swap12` on `Fin 3`. Check all inputs in both directions; the existing concat clients send 0 to 2 in one order and 1 in the reverse order (`Examples/FiniteUniverseLoops.lean:156–180`). Compare direct, interpreted and any normalized/table-prepared route on the same conversion chains and complete package workloads, including zero requests, one request, repeated requests, and an explicit representation change/rebuild. Include an inverse pair but preserve positive executed baseline costs. Include a chain without adjacent cancellation to avoid selecting syntax only on its best case.

The state test must observe every demanded intermediate output and the invariant, not only the final state. Reuse `wrongPresentation` and `wrong_rejected` in `CubicalFiniteStateIdentity.lean:88–111`: a bijection fixing the initial state fails the transition contract. The implementation should prove a universal simulation for the selected package and command fragment; finite tests are additional execution evidence.

Syntax earns inclusion if a concrete workload needs inspectable recipes, or if a measured normalization strategy saves complete work at the admitted workload sizes and its setup/storage costs are acceptable. If the same benefit follows from direct batch execution or finite tabulation, prefer that smaller interface unless another client needs syntax. A broader evaluator earns inclusion when a named source program cannot be represented without discarding a required observation or witness and the proposed evaluator supplies that capability under explicit hypotheses.

Established boundaries are noncomputability of the native target, the PLift/discrete scope of package recovery, and the limited tariffs of existing memoization models. Performance superiority, ease of the new proof adapters, native allocation and general author usability remain unmeasured. This assessment found no defect in an implementation of #533; it evaluates candidate designs before that implementation exists.
