# Implementation and use assessment for #533

Recommend retaining direct supplied equivalences as the primary executable interface. Add a bounded identity/composition/inverse syntax only as a comparison client, with a separately charged interpreter and any proposed normalization. The inspected native comparisons already support executable finite maps and the complete finite state package. They do not require callers to construct transport syntax. No wider evaluator is justified by this workload.

This is an independent implementation/use assessment at accepted source `14aa5ef722ea4b5c2e9dadac3ff448da9ec8bb18`, permitted by the assignment. I had no prior implementation involvement, read no other assessment, contacted no other agent, and ran no Lean builds or executable experiments. Recommendations below are proposed implementation obligations, not newly checked proofs. Source locations are relative to that revision.

## Existing usable boundaries

The direct semantic bridge is already unusually small. `Examples/CubicalUnivalenceTransport.lean:24–61` defines actual `codeTransport`, decodes its result in `observed`/`value`, and proves `value_eq`. An executable forward function with an erasure equation to `e s` can therefore prove agreement with the actual decoded endpoint by composing with `value_eq`. Its inverse counterpart must use the chosen reverse endpoint when reverse transport is the advertised operation: `Examples/CompositionalUnivalence.lean:66–77` provides `observedInverse_eq`. Merely invoking `value_eq e.symm` would establish ua of the supplied inverse; that is a different named semantic endpoint until connected to reversal.

For composition, `observedConcat` applies `pathToMap` to actual selected concatenation, and `observedConcat_eq` identifies its observation with `d (e s)` (`Examples/CompositionalUnivalence.lean:44–55`). Thus a direct adapter need not hide a syntax tree to preserve native composition observations. `Examples/FiniteUniverseLoops.lean:156–175` supplies two executable swaps whose composite is direction sensitive: input 0 goes to 2 in one order and 1 in the other. Their composite is a suitable noninvolution control. Boolean negation by itself would miss a reversed-map bug.

The finite package is already available as executable data. `Examples/CubicalFiniteStateIdentity.lean:13–54` defines `Phase`, `presentation`, `machine`, `presentedMachine`, `observer`, and direct conjugated operation. The native counterpart `machineTransported` is connected by whole-package equality to `presentedMachine` at lines 73–85. That equality follows from `targetPackage_eq`, whose definition reads the actual filled native package through its endpoint decoder (`Examples/CubicalStructuredState.lean:308–324`). Reusing this client preserves initial state, step, invariant, and proofs, rather than substituting a new package with a theorem only about matching output numbers. `wrong_transition`, `wrong_rejected`, and `wrong_path_rejected` already distinguish initial-state agreement from operation preservation.

Keep native objects and their proofs on the specification side. The supplied executable maps, finite state, and operations belong on the executable side. In particular, deriving a permutation from an arbitrary semantic loop with `loopPermutation`, or an inverse through `admittedCarrier`, is not an executable extraction API: these declarations are noncomputable. A supplied finite permutation needs no such extraction. The finite package's Prop-valued invariant proofs do not make a choice-based data definition executable merely because proof terms erase.

## Resource API fit and caller obligations

`Applications/Resources/Measured.lean` already gives value/cost pairs, ordered `bind`, erasure composition, and tariff reweighting. Its `same_value_different_cost` explicitly rejects deriving a cost equation from output equality. `Applications/Resources/Workload.lean` provides `run`, `run_append`, `run_invariant`, and `run_value_fusion` for actual state transitions. Use these for the machine: its state changes after each operation.

`Resources.Prepared.Ops` instead models queries against retained preparation. `answer : R → Q → Measured A Nat` does not return an updated representation. `Prepared.queries` repeatedly uses the same `r`. It fits an immutable prepared finite map or precomputed transition table, but it is not itself a mutable state-machine executor. A small client can prepare a static map/table using `Prepared`, then use `Workload.run` for evolving state, or simply use measured setup followed by `run`. A new generic state/preparation framework would add obligations without filling a demonstrated gap.

`Prepared.Reduction` already charges static conversion, query encoding, and answer decoding. `Storage`, `Bounds`, and `Maintenance` separate retained cells and validity after updates. `Bounds` alone does not certify maintenance: its maintenance profile needs a corresponding executable `Maintenance` witness. This is an established API limitation to honor, not a defect requiring a redesign.

The parser is a concrete precedent for a syntax comparison, not permission to assign costs to arbitrary functions. `Applications/Languages/ParserWorkload.lean:130–147` measures actual `Map.run` recursion and proves its result agrees with the supplied isomorphism; lines 256–326 separate setup from query events and give exact repeated-use totals. Its source graph and query arena policy are explicit. `Examples/ParserWorkload.lean:59–74` checks that combined preparation helps one repeated workload but loses on the short one. Retain these controls. Their tariff and source-tree storage convention cannot establish physical allocation or cache behavior for a new finite transport implementation.

## Smallest complete implementation

Freeze Bool negation, a `Fin 3` permutation with distinct forward/reverse action, and the existing Fin 3/Phase proof-bearing machine. Supply measured forward and backward functions and measured machine initialization, step, and observer. Prove their value projections against the supplied equivalences and executable package, then bridge to the native endpoints above. Include a theorem for arbitrary finite operation words, not only the first transition from idle. Test failed state as well as valid reachable states so an implementation that collapses all states to ready cannot pass the full operation contract.

For the syntax candidate, use only the selected finite primitives plus identity, composition and inverse. Define its actual recursive executor; charge dispatch and primitive conversions. A proposed normalization must have its own setup algorithm and preservation theorem. Algebraic inverse cancellation in a proof does not erase conversions already executed by the baseline. If normalization compiles a permutation table, count the table construction, retained cells, and lookup work. Both candidates must retain an ordinary direct call path with no required AST construction.

Keep construction assumptions explicit. A generic `Equiv` argument permits computable instances but supplies no source tariff for its opaque functions. Either supply measured map implementations with erasure laws, or restrict the executable instance to the named finite primitives. Exclude native decoder admission/elaboration from runtime counts explicitly and charge every executable conversion that is actually performed. Proof checking and runtime execution are different phases.

## Matched workloads and discriminating test

Compare identical input states, operation words, and observation schedules. State whether initialization and final observation occur for an empty word. For an eager setup policy the zero-use workload still pays setup; a demand-driven alternative is a different executable policy and needs its own definition. For conjugated unary steps, the executed work includes backward conversion, the source step, and forward conversion. Observing a state is another measured operation, not a free projection unless the declared model specifies that event as free.

Use the same words at zero, one, and repeated lengths for direct and syntax policies. For each, establish equal full observation sequences and exact setup-plus-actual-step-plus-observer totals. If a retained source-state strategy moves conversions to observation boundaries, prove its relation to target state after every step. Account separately for simultaneously retained source/target values or tables. This can change the work tradeoff, but is not ordinary inverse cancellation.

The discriminating test is a mixed workload containing a noninvolutive forward map, its reverse, machine steps, and observations between operations. Run it under direct execution, raw syntax, and any normalized/retained policy. Exhaust the finite input states. Require the semantic observations to agree with the actual ua/concatenation/reverse endpoints, while expecting raw forward-then-reverse to retain positive modeled work. Repeat at zero and one use so setup cannot disappear into an amortized statement. Change a retained static permutation or machine version and require either rejection of stale state or charged rebuilding before use. If the design chooses immutable retention, make replacement end the old session and charge new setup; do not claim a zero-cost update capability.

This test can justify syntax if normalization reduces complete work for repeated use without unacceptable retained storage. If the supplied direct composite is equally usable and as cheap under the same charged operations, syntax has not demonstrated an additional capability. That outcome supports shipping the direct adapter and preserving syntax as a bounded comparison rather than a mandatory realization boundary.

## Risks and validation limits

Established facts are the existing semantic bridges, executable finite package definitions, and separation of measured operations from prepared/static queries. The anticipated risks are accidental omission of closure/setup work, using pure queries to model state transitions, substituting ua of an inverse for selected reverse transport without its bridge, and hiding noncomputable data dependencies behind proof erasure. I found no inspected evidence that these risks make the direct route impossible.

No runtime speed or allocation conclusion follows from this assessment. Acceptance still needs executable tests of the new functions, statement review of each new formal claim, the repository build/proof audit, and a dependency audit distinguishing choice in specifications from executable data dependencies. Any timing experiment should name the compiled entrypoint and toolchain and report elapsed time separately from source-event counts. This report makes no external literature claim and needs no new kernel axiom, general normalization result, or Wasm work.
