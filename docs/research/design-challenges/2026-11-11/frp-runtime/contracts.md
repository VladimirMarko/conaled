# Contracts and foundations assessment

Assessment date: 2026-11-11. Baseline: `1ecdea2376786920a043009a35712a5dec93723a`, supplied source archive and neutral candidate packet only.

Retain the candidate's local semantic contracts and separate execution realizations. Change the first experiments to test the connection between phase queries, delivery ticks and continued state before treating a demand graph as their common execution architecture. The archive supports several useful compositions already. It does not yet establish that their observation boundaries coincide. I recommend a small synchronous composition experiment and an early between-ticks migration experiment; neither requires a general scheduler or native emitter.

The strongest case for retaining the candidate is concrete proof reuse. `ReactiveCompiler.realize_compile` identifies the compiled initialized machine with independently evaluated source semantics. `Progress.Feedback.run_related` preserves an entire ordered finite output list and its final-state relation from arbitrary related starting states. `Pipeline.response_run_related` and `run_consumer_related` already lift this result through silent engine positions, while `compiled_reference` connects compilation to packet-driven execution. `Examples/ReactivePipeline.lean` uses those universal results and distinguishes silence from an emitted empty batch. `Indefinite.Program.service` additionally supplies circuit execution derivations and a uniform arena bound. These are compatible building blocks, not merely similarly named interfaces. The candidate correctly avoids deriving physical deadlines, executable state conversion or external acknowledgment from them.

**CF-1. The phase-query and delivery-tick boundary is the earliest unresolved composition contract. Status: established distinction; missing bridge in the proposal, not a demonstrated contradiction.**

`Applications/FRP/Spec.lean`, declarations `Behavior`, `Event.switcher` and `denoteRNF`, give a value at a real timestamp independently of how often it is queried. `Applications/Progress/Feedback.lean`, `Solution` and `state`, advance on a natural-number tick. `Applications/FRP/Pipeline.lean`, `responseMealy`, advances once for every emitted batch, including an empty batch, and never for silence. `Examples/ReactivePipeline.lean` explicitly checks that an empty delivered batch increments the joint consumer to `(1,0)` while silence leaves `(0,0)`. `Exclusive` permits a new request after completion, including at the same timestamp; its occurrence labels are proof-only and distinguish accepted occurrences (`label_accepted`, `at_most_once`). Thus a timestamp is not a tick identity.

A scheduler that memoizes a phase query by timestamp may safely share the pure value while still owing two consumer transitions for two accepted requests. Conversely, evaluating a dependency twice must not itself advance a shared delayed consumer twice. The candidate specifies repeated queries in A and cancellation/shared dependencies in D, but does not yet select this boundary for their composition. “Explicit delayed edges” is insufficient until the tick that advances each edge is specified. This also determines whether two ready requests may be committed in completion order: a one-tick delay receiving `false,true` versus `true,false` has different ordered output and residual state even though both demands were delivered exactly once.

Smallest correction: state separate pure query and accepted-tick operations, then select a serialization/commit order for stateful consumers. Reuse `Pipeline.responseMealy` for the existing delivery interpretation. Add no new simulation law until this interpretation is chosen. A synchronous runner with one outstanding tick can establish the boundary first; a later scheduler can refine it with internal stuttering and bounded buffering. Existing clients retain their delivery semantics. A new graph API that intentionally coalesces repeated requests must expose that as a different contract.

Discriminating paper test: query a constant phase twice at one timestamp, feed both accepted deliveries through a composed delay, and repeat with an empty batch and an inserted silent scheduler step. Compare ordered outputs and final state. Then allow the two dependencies to finish in reversed order. Require either identical committed observations or explicit rejection of the reordered commit. The first test needs no asynchronous machinery and could fail an otherwise sound phase evaluator.

**CF-2. An active phase alone does not represent all information allowed by the current frontier protocol. Status: established representation restriction; candidate leaves the correcting retention choice open.**

`Frontier.windowValid` requires every timestamp in a packet to lie in the newly closed interval. It does not require timestamps within the packet to be increasing. `Frontier.batch` preserves occurrence order at each timestamp; `Event.past` sorts timestamp support before folding the batches. Therefore a phase evaluator must sort or otherwise select chronologically, preserving packet order only within equal timestamps. It cannot fold the packet list indiscriminately. For a hypothetical admitted window `[0,3)`, a packet containing a change at `2` followed by a change at `1` has the change at `2` active at query `5/2`, despite its earlier list position. This is a paper counterexample, not a new Lean check.

There is a second storage boundary. Suppose initial phase is zero, a change at `1` selects constant one, and the source frontier advances to `3`. Keeping only the latest selected phase cannot answer a query at `1`, whose answer is still zero under strict switching, or a query at `1/2`. A retained lower bound of zero admits both. Even monotone queries can be behind an already advanced source frontier. `RetainedLifecycle.step` checks the query lower bound and pending conflicts, but its retained machine still keeps the cropped source log. Its theorem is not a license to replace that log by a latest-phase pointer.

Smallest correction: choose one explicit invariant: a phase cursor advanced only through changes strictly before the current query, with bounded pending changes; or a bounded queryable phase history plus its predecessor phase at the lower bound. The finite catalog may instead remain available and be rescanned, with its cost charged. A monotone-query restriction alone does not remove pending-future storage. A timestamp equal to the next change must leave that change unapplied, even when the source has already certified it. Rejection after capacity exhaustion is compatible with the candidate's admitted execution class.

Discriminating tests: the unsorted packet above; a query exactly at a known change; source completion far ahead of a monotone query sequence; two changes at the same timestamp; and pruning exactly at a switch boundary. These refine A's existing boundary tests rather than requiring another runtime abstraction.

**CF-3. Between-ticks migration is a cheap test of the state boundary and should not wait for general scheduling. Status: supported sequencing alternative.**

The candidate already says G need not wait for C. The code supplies an especially small starting pair: `Examples/IndefiniteService.lean:72`, `redundant`, represents one delayed Boolean by `(x,!x)`; `related_step` proves step preservation and `redundant_output` consumes the generic transport theorem. The paper transfer `x ↦ (x,!x)` constructs the relation, and projection back to the first coordinate works on its reachable invariant. This offers different representations without new source syntax. It is not an implemented migration protocol.

`run_related` needs the relation at the transfer point, not the original seed relation. `Feedback.transport` can similarly be applied to machines reinitialized at their current states. Consequently continuation preservation after a successful transfer is largely an existing theorem application. New obligations belong to executable transfer, reachable-state validity, admission pause, failure and exclusive commit. Repeated migration can compose those boundary obligations; it does not require a new universal continuation-equivalence framework first. Equality of last output remains inadequate, as the candidate observes.

Smallest correction: test an explicit requested transfer immediately after the first synchronous stateful client, alongside or before policy measurement. B's two targets use `Val B s` as the state carrier through `ReactiveCompiler.realize`; merely selecting those targets does not test representation conversion. Use the existing redundant client or a reordered-register pair to exercise that missing capability. Keep policy ranking optional. Charge coexistence of both representations and define a precommit failure that preserves the old state.

Discriminating test: process a nonempty Boolean prefix, transfer both directions, then enumerate finite suffixes against uninterrupted execution, including a suffix exposing reset-to-seed. Follow with a universal suffix proof through `run_related`. This preserves existing circuit clients and adds no new compiler requirement. It cannot establish pending-IO migration, for which the candidate correctly demands a separate successor.

**CF-4. Numerical endpoint correctness must not silently become a phase-query theorem. Status: established scope boundary; unresolved implementation choice.**

`CheckedMotion.checkedStep_correct` relates the successful rational endpoint packet to `Tick.decode.finish`, conditional on the incoming `Approx` relation. `NumericalExecution.run_correct` relates successive endpoint samples and final state to exact commands. `run_clock`, `run_error` and `run_append` already establish elapsed-clock accounting, carried error and finite composition. `run_interval_correct` relates the final result of repeated constant-control steps to the exact trajectory at that endpoint. None of those statements provides a value/error certificate at an arbitrary interior query time. `NumericalExecution.run` also rejects the entire run on a failed tick; a driver retaining a committed prefix supplies an additional operational contract.

The candidate recognizes the need for a source-time/control bridge. That bridge should determine query admissibility before choosing a shared phase interface. The exact disk trajectory, the approximate packet and the strict switch timestamp have different roles. Subdivision is justified by `trajectory_add`/`execute_replicate`; interpolation needs a different theorem. Carrying the old error across a switch is already supported when the new control continues from the old endpoint, but a state reset or representation conversion needs its own relation to that endpoint.

Smallest correction: first admit endpoint queries only, or split the last interval to end at the query and prove its clock correspondence. Make an arbitrary interior-query promise only after constructing a dense-output certificate. The exact affine alternative in E can test clocks and switches, but a zero-error exact example does not test propagation of accumulated approximation; retain a nonzero incoming-error case if this alternative is used to assess that contract. Move this thin numerical composition test before a general demand graph if hybrid semantics is a priority.

Discriminating test: switch controls after a nonzero-error packet, query at the boundary and inside the next interval, and resume after a rejected proposed step. Compare accepted endpoints, elapsed time and error against the existing exact command sequence. Reuse the existing numerical recurrence instead of adding an independent “error survives switches” field that merely assumes its conclusion.

**CF-5. Recovery and pending migration need a sufficient observation state, not just machine and queue contents. Status: existing negative evidence supports the candidate's stronger contract.**

`Durability.Protocol.SpecStep` distinguishes commit, acknowledgment, crash and recovery. `Step.publish` makes the root authoritative only after persisted writes; `Step.acknowledge` clears a volatile active request and is not a theorem about a remote effect. `DriverIO.publish` explicitly treats a successful flush as local publication. These contracts cannot on their own settle whether a peer applied an output whose acknowledgment was lost.

There is related checked evidence beyond the FRP modules: `Examples/InteractionPrefixes.lean`, `stages_do_not_determine_client`, separates initially idle from delivered-idle histories although their internal stages agree. `cannot_recover_stage` separates internal prefixes erased by the external projection. `PrefixClientObservation.buffered_pending` shows a buffered answer is still externally pending. These are source-inspected Lean declarations, not runtime measurements. They explain why current machine state or last output alone is too weak for migration/recovery.

Retain F's peer contract and G's publication-status transfer. Select the external observation before compressing history: it may be a justified finite summary, but the diagnostic's full history should not be copied into a claimed bounded runtime by default. Neither the interaction observer nor `Protocol.Machine.used : Set Nat` is a bounded-memory implementation. The candidate already flags the unbounded-identity issue; this is supporting evidence, not a newly discovered omission.

The smallest useful experiment is one pending output with a stable identity, a peer effect and a lost acknowledgment, followed by migration or crash. Compare against the chosen deduplicating or at-least-once observation. This can run over a single synchronous consumer and does not depend on a general graph scheduler. An abstract atomic ownership commit establishes only the modeled transition property; crash persistence remains F's additional obligation.

Taken together, these findings favor an experimental sequence of: choose and test the phase/query-to-tick boundary; construct the bounded rational evaluator with explicit pending/history retention; test a current-state representation transfer; connect one numerical endpoint client; then decide whether a demand graph removes recurring client work. Startup choice and artifact emission remain useful independent compiler clients, but success there provides little evidence for the phase/scheduler coupling. The synchronous alternative preserves ordered output, residual state and conditional service while deliberately limiting concurrency. It provides a reference semantics against which D can establish schedule independence. No existing denotational or circuit theorem needs to be discarded.
