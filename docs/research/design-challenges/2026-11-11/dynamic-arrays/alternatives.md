# Dynamic arrays: alternatives and generality assessment

Recommendation: keep two named policy steps and reuse the existing measured runner, with a small shared implementation of allocation, ordered copying and writes. Compare that design with two direct local implementations before selecting a storage interface. The evidence supports shared observations and copy proofs; it does not yet establish a need for a storage hierarchy or a policy language. Both alternatives can preserve every requested observation. Neither needs to change the fixed-buffer API.

This is an assessment of pinned commit `e80c51d968925be3809ba3acc3259de7041b504b`, not an adoption decision. Paths below are relative to that checkout. I had no prior involvement in this design in the supplied context, read no other assessment, and did not coordinate conclusions. I used the assigned fresh context. No model diversity is established.

## What the current code establishes

The strongest retention evidence is `Applications/Resources/Workload.lean`: `Resources.run` executes each step on the actual state returned by its predecessor; `run_append` preserves that intermediate state; `reweight_run` transports any additive-monoid homomorphism, with no commutativity assumption. `run_invariant` and `run_value_fusion` already separate invariant preservation and semantic decoding from execution. These are the desired trace mechanisms without a new interpreter interface.

Concrete clients demonstrate reuse rather than merely suggest it. `Resources.BoundedSummary.run_erasure`, `plain_cost`, `cached_cost`, and `sequential` in `Applications/Resources/BoundedSummary.lean` derive client results from that runner. `Resources.ByteBuffer.projected_cost` in `Applications/Resources/ByteBuffer.lean` transports a concrete machine's event projection through the existing cost theorem. `Resources.RandomAccessCosts.bulkRun_append` and `bulkRun_reweight` in `Applications/Resources/RandomAccess/Observation.lean` use the same trace laws for a different representation. These justify retaining the runner independently of the array representation decision.

`Dijkstra.Store.accum_lookup` in `Applications/Dijkstra/Store.lean` is another retention point: repeated indices are admitted and interpreted in order. Only `valuesAt_map_unique`, the specialization to a simultaneous unique-index result, asks for `Nodup`. This is the right separation between operational domain and a stronger corollary's assumptions. The fixed `Fin n` index domain does, however, prevent using this API unchanged as a raw executor admitting out-of-bounds indices.

The existing byte machine supplies a useful bounded realization, not dynamic-array evidence. `Sequences.ByteBuffer.Machine` fixes `N`, requires `N ≤ W`, and stores its size in `Fin (N+1)`; `push` requires room and `step` rejects overflow. `Examples.ByteBuffer.zero_capacity` proves refusal at capacity zero. `convert` copies the entire fixed store and preserves its decoding; it does not prove arbitrary copy windows or resizing. The concrete clients `replies`, `full_rejects`, `invalid_reply`, and `failed_trace` exercise bounds, invalid caches, and environmental failures. Those contracts should remain available unchanged.

Searches of integrated `Applications/`, `Examples/`, and `SquareKit/` found no `DynamicArray` or `DynamicArrayEager` implementation. `docs/research/adwh-reconstruction-map.md` explicitly lists their resizing and ordered trace obligations as remaining work. Thus there is no integrated policy implementation to reject or preserve wholesale. The recovered notes describe acceptance requirements and proposed mechanisms; their short policy table is explicitly source-only evidence, not a checked local result.

## Alternatives worth comparing

| Foundation | What it preserves | What must still be proved or chosen |
|---|---|---|
| Two direct policy steps over one concrete raw store, sharing copy lemmas | Full raw-state domain, policy-specific control flow, named event traces, existing `run` laws | Each local step's layout and potential lemmas; agreement between direct copying and the shared copy theorem |
| Shared primitive storage operations, two policy steps composed with `Resources.bind` | Same capabilities, with allocation/copy/write order expressed once at primitive boundaries | Exact primitive raw behavior, copy windows, layout preservation and policy potentials; benefit over direct code must be demonstrated |
| Explicit command programs interpreted against storage backends | Same capabilities if the language retains raw indices, source reads, allocation sizes and insertion boundaries | Interpreter semantics and simulation laws; a second backend or program transformation would supply evidence that this extra layer pays for itself |
| Valid dependent carrier as the only executor domain | Strong static layout guarantees and convenient valid-state clients | Cannot express the requested malformed raw states; unsuitable as the sole foundation, though useful as a derived client API |

The first two are close alternatives. Shared primitives need not mean a record with laws or a datatype of programs. Functions producing measured states can be composed directly. `Resources.bind_assoc` and `reweight_bind` already provide the relevant algebra. Introduce new law fields only if an abstract backend needs them and concrete definitions do not already derive them.

A defensible different foundation is a raw finite list/array with total update conventions, followed by a layout predicate and a refined valid carrier. Another is a total indexed store with an explicit capacity observation. The latter makes out-of-range reads easy to state but has to relate its unbounded function to finite allocation, initialization and copy behavior. Neither requires an adapter to `ByteBuffer` for admission. The decisive condition is recovery of the requested source semantics over its entire raw domain. A total indexed store must not silently invent observable default values that alter that domain, while a finite store must not silently reject commands the source executes. The pinned integrated code does not settle which convention matches the recovered source.

An explicit command language becomes useful if there is a real second storage realization, or if copy scheduling is itself transformed and verified. It is otherwise an additional representation of behavior already expressible by measured state transitions. A future byte realization would need its own finite-word, allocation-failure and ownership contract, as the existing byte machine already documents. Pure vector equality alone cannot establish physical separation or runtime cost.

## Preserve information before selecting tariffs

Use an ordered list of primitive events, with enough payload to state the original prices, as the primitive observation. An allocation of zero slots must remain an allocation event. Collapsing observations immediately to work, slot count and growth count cannot support every price over a richer event alphabet, even when the chosen counters happen to distinguish the supplied examples.

Paper argument: if `p [] = 0` and `p (xs ++ ys) = p xs + p ys`, induction gives `p [e₁,…,eₙ] = p [e₁] + … + p [eₙ]`. Thus an arbitrary original additive list price is determined by its singleton prices, and can be packaged as an additive homomorphism from the list/free additive observation. This is exactly the shape consumed by `reweight_run`; the source-price packaging lemma remains to be checked. No commutativity is needed. Equality for all additive observations includes the identity into the ordered list observation, so count equality is strictly weaker than that universal claim. If the original price codomain is only `Nat`, its prices alone cannot distinguish event permutations; the independent ordered-trace requirement still must.

Insertion boundaries need separate information. A small canonical observation is a list of event blocks, one block for each insertion, including an empty block if an insertion emits no primitive events. Flattening recovers the primitive trace; mapping a price over blocks recovers per-insertion bills. Primitive copy loops can accumulate flat traces locally and the enclosing insertion can wrap its result as a singleton block. The alternative is one flat trace plus a separate boundary log, but that creates a consistency obligation.

The inability to recover grouping from flattening is a mathematical obstruction, not a missing library theorem: `[[a,b]]` and `[[a],[b]]` flatten to the same list and retain different boundaries. This paper counterexample justifies adding boundaries to the observation, rather than requiring a nonexistent reverse homomorphism. Both policy implementations must retain their own event order; equal final sequence values do not imply equal event traces or prices.

## Copy and potential obligations remain separate

A shared copy theorem must quantify arbitrary preexisting prefix and suffix. Proving a copy into freshly zeroed storage is insufficient. The theorem must also say whether reads use a fixed source snapshot or the changing destination. For a hypothetical overlapping same-store copy, copying indices `0,1` to `1,2` in `[a,b,c]` gives `[a,a,a]` under left-to-right live reads but `[a,a,b]` under snapshot reads. These are different operations. A simultaneous specification may need nonoverlap or snapshot hypotheses even when the sequential executor itself needs none. Do not insert those hypotheses into raw execution to make a convenient specification true.

`Resources.run_potential` and `run_potential_exact` in `Applications/Resources/Potential.lean` already retain both endpoint potentials and arbitrary initial state. Their local premise quantifies every state, however. If a policy's local potential inequality holds only under layout or positive spare space, this theorem cannot be invoked directly on all raw states with that restricted premise. Prove an invariant-restricted variant, or specialize the potential argument to a valid carrier while retaining the raw executor separately. This is an application obligation, not evidence that every raw state should be excluded or that the existing theorem is wrong. `initial_potential_matters` supplies an existing checked counterexample to dropping the initial term.

All additive price transport and an amortized bound for a particular tariff are separate promises. A policy potential proving a work bound does not automatically prove the same numerical bound for arbitrary event prices. State the tariff assumptions of each amortized result explicitly. Neither policy should acquire a universal cheapness claim from a single work specialization.

## Discriminating acceptance cases

1. Run both policies on the same three- and four-insertion inputs from the recovered notes, asserting final content, capacities, free space, exact ordered blocks and each displayed work/allocation/growth projection. The notes predict eager is cheaper in work after three insertions and literal after four; these remain fixtures to check, not results proved in this assessment.
2. Copy a nonempty interval into a preexisting destination with nonempty prefix and suffix; add empty windows, repeated destination indices, overlapping reads where admitted, and out-of-bounds raw commands. State raw equations first and only then the conditions for a simultaneous window theorem.
3. Execute from zero capacity, a full singleton, a non-power capacity and a malformed cursor. Confirm that raw execution and pricing remain defined on the intended domain while layout-dependent conclusions ask for the precise invariant. Check allocation-zero still contributes one growth event.
4. Compare flat and grouped observations using the paper collision above. Use identity observation to test order, a zero tariff, an allocation-size tariff, and a tariff distinguishing event payloads omitted by any proposed counter representation.
5. Check empty and concatenated insertion lists from an arbitrary raw state. For potential results retain both endpoint terms, test a nonzero initial potential, and identify exactly where layout or positive-free-space hypotheses enter.

The smallest useful next step is to implement one arbitrary-window copy operation and both named insertion steps in an isolated comparison, using the existing runner and grouped observations. Compare direct steps against shared primitives on these contracts. A new storage hierarchy should follow evidence of a second interpretation or repeated obligations beyond those already handled by `run`, rather than precede this comparison.
