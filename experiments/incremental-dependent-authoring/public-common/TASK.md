# Fresh incremental task: finite arithmetic schedules with selected dependent output

Use the independent `Examples.IncrementalDependentTrialSpec` supplied with this
handoff. It defines instructions successor/double, left-to-right schedule
execution, the dependent packet type, two substitutions and numerical oracles.
This task was selected after the reviewed #355/#356 interface freeze. It is not
a previous trial task or the reserved #108 task. No route solution was prepared.

The extension is a client family parameterized by **an arbitrary finite schedule**,
including empty schedules and concatenation. The earlier public #356 example is
one fixed nested expression; changing only its numerical constants does not
complete this task.

## Required mathematical outcome for both routes

For every `ops : List Op` and `n : Nat`, construct and connect the following:

1. A source index expression generated by the schedule from the one free natural
   variable, and the raw dependent term `snd N B (pair N B (s index) (t index))`.
   Here the independent meaning is B(k)=Fin(k+2), s(k)=k+1 and
   t(k)=k+1:B(s(k)). Construct its actual native typing derivation in Γn and its
   target derivation via the retained F inclusion and fullG compiler. The target
   raw expression must be the actual pack/dependent-split quotation. Reuse the
   native rule system; do not replace native typing with an unrelated predicate.
2. Executable source and target representations of this generated program,
   a quotation connection to those actual raw expressions, and a theorem that
   target execution returns `Spec.selected ops n`, retaining both the index and
   chosen component. The executor must compute arithmetic, construct the pair
   and project/eliminate it. It must not call `Spec.run` or `Spec.selected` as its
   implementation, choose a constant answer, or use a proof tree as its runtime
   carrier. A recursive index-expression executor with explicit pair/observation
   operations is an admissible native representation. Existing executable APIs
   are permitted. No arbitrary full-calculus semantic interpreter is required;
   state the bounded generated-program image being interpreted.
3. Derive a schedule-concatenation law for the chosen code/semantic route:
   running the generated index for `xs ++ ys` agrees with first running xs and
   then ys, for arbitrary lists and input. Connect this to the selected dependent
   output (the final pair is constructed after the complete schedule). Retain a
   checked empty-schedule case and the two-stage F/G proof translation connection.
   A theorem solely about the supplied Spec.run, disconnected from your generated
   program, is insufficient.
4. Apply the actual typed substitutions n:=s(k), then k:=d(m). Connect the
   resulting raw term and dependent type to the executable program and prove
   its output is `Spec.selected ops (Spec.sigma (Spec.tau m))` for every ops,m.
   Both substitutions must be justified in the native rule system. Raw G
   substitution compatibility may be reused; no equality between unrelated
   native proof trees is demanded.
5. Use these general results to recover `Spec.demoAnswer` for demo at 3 and
   `Spec.substitutedAnswer` for the twice-substituted demo at 3. Reject
   `Spec.wrongAnswer`, which has the same dependency index and an inhabited fiber
   but a different selected component. These numerical cases must call your
   general results. Directly proving only the oracle calculations is insufficient.

All equalities here are Lean propositional equality of the indicated selected
values, syntax or code. Object-language typing remains the native judgment.
There is no assumption of global decidable equality, reflection, all-target
soundness, proof irrelevance for derivation data, or arbitrary higher identity.

## Route restrictions

- Native arm: use the supplied pre-#356 native rule/translation interfaces and
  direct code/semantic reasoning. Local helpers are allowed. The candidate
  branch semantic fold and shared proof/code wrappers are not available.
- Compositional arm: use the supplied reviewed #356 interfaces to derive the
  generated client's preservation through local/compositional reuse. The final
  application must visibly consume a public whole-proof/code/joint preservation
  result. Directly re-proving every result while bypassing those interfaces is
  not the candidate route.

Both arms have the same mathematical outcome above. Extra generality or optional
capability wrappers are not required for native success and receive no bonus.
Do not edit frozen library files. Implement the new client and helper definitions
in self-contained attempt modules. You may inspect all public files in your own
