## Question and allocation

Compare direct native Lean with the finite-registry CLI on identical H1/H2
contracts. Both routes may use the same native preservation theorems. One fresh
independent author per arm; both do H1 then H2, with no crossover. They must not
have implemented the prototype or seen reference solutions. The implementer
has seen task descriptions but no private solutions/transcripts. These are
held-out proof/application clients, not blind discovery or unknown theory tasks.

The checked task statement files and private reference validation hashes are
frozen separately by the coordinator. H1 tests selected-row extension on a
nonconstant-in-code Option Bool evaluator whose individual rows are constant
in the input; H2 tests actual compiled total execution through a product cost
observation. The mathematical expectations remain the proposed contracts in
the preparation record, subject to prospective independent statement review.

## Source access and prompts

The coordinator supplies isolated pinned handoffs with identical native source
allowlists, dependencies, task/support files and these conduct rules. Direct
excludes the CLI source, registry, route transcripts and generated proofs.
Assisted additionally receives the frozen CLI, docs and data registry. Both
exclude prior author trials, private references, the other arm and repository

Exact route prompts, handoff paths/HEADs, source hashes and allowlist are required
fields of the final launch manifest. Prompts must state the task, route exposure,

No delegation, task-specific external assistance, production edits or private
coordinator hints are allowed. Environment repairs are logged. Mathematical
coaching ends the independent attempt; subsequent work is labeled post-trial.

## Enforced budget and cutoff

Each arm receives 45 elapsed minutes and 30 actual Lean feedback invocations
across both tasks. The coordinator starts the state immediately before dispatch.
Reading, reasoning, writing and checker time count. There are no unlogged time
exclusions. Provision dependencies and neutral smoke checks before starting the
clock. Schedule one active author arm at a time on CPU 0, with no other project
build using that CPU/lock; record launch order and host contention. This is a
bounded comparison, not a causal timing experiment.

Both arms use `interpretation-trial-check.py` for every Lean feedback invocation.
The assisted CLI passes its state through `CONALED_TRIAL_BUDGET`; before every
internal check the external runner atomically tests/increments the same counter.
Requirement inspection, failed evidence, generated-result checking and author
requested audit feedback all count. Version/metadata lookup and the neutral
prelaunch smoke check do not supply proof feedback and are not rounds.

The runner stores source snapshots before executing Lean, commands, timestamps,
exit codes and diagnostics. It refuses checks at either cap. An already-started
check may finish without further edits or checks. The coordinator runs its
independent `--watch AUTHOR_OUTPUT` process at dispatch; at the first observed
cap it snapshots output and records the snapshot interval. It polls at 0.2-second
intervals; this is a documented bounded observation delay, not an instantaneous
filesystem snapshot. The coordinator interrupts the author at cutoff and retains
both the cutoff copy and already-started checker snapshot. No post-cutoff changes
count as author results.

The state and watchdog live outside the author output. Authors may not reset,
edit or bypass them. This access agreement is not an OS sandbox. Any detected
bypass invalidates effort comparison and is reported; retain mathematical
artifacts separately. Logging, wrapper or watchdog failure stops the arm and
freezes available artifacts, marking timing/effort unavailable. Do not silently
fall back to unlogged Lean or extend a budget after observing an outcome.

## Fixed scoring and fallback

Native fallback is allowed in both arms within the same budget. An assisted
author who uses only native Lean may pass mathematics but provides no positive
evidence of successful tool use. Record three separate outcomes:

1. Mathematical completion: all mandatory task checklist items checked under
   unchanged assumptions and observation.
2. Tool completion: an actual checked generated application is used in the
   final proof, with receipts linking its source/certificates to that result.
3. Work removed: specific obligations, application terms or diagnostic repairs
   supplied by the tool, compared with the direct artifact. This is qualitative
   when reading/search activity is not exhaustively captured.

For H1, mandatory items are extension at omitted `none`, retained selected
`some false` code and false value, universal representation, nonsurjectivity,
image-only domain distinction and checked false-source rejection. For H2 they
are both additive laws/packages, composition through the product, actual
seed/transition execution equality, universal `7*(1+2*length)` cost and sum value,
native recoveries, the two concrete cases and shifted-zero rejection. Alternative
valid sufficient interfaces/proofs pass; no unique spelling or weakest law is
required.

First-attempt success means the first actual checked source snapshot submitted
for that task satisfies its entire checklist. Intermediate CLI obligation checks
are counted rounds but not complete task submissions. Final pass satisfies every
mandatory item before cutoff; partial means at least one mathematical item is
checked but others remain; fail means no mandatory item is established; unavailable
means a provisioning/tooling failure prevented assessment. A tool failure can
coexist with a passing native mathematical fallback. Diagnose environment,
mathematics, API/encoding and author repairs separately.

Retain every attempt and unsuccessful diagnostic. Count checker rounds and
elapsed time from logs; record manual obligation proofs, generated applications
and repaired goals by declaration. API searches, reading and subjective diagnostic
usefulness are qualitative unless a complete log supports counting them.
Prototype construction, task preparation and provisioning costs are separate
from author work. Small samples and author/order differences prohibit a general
productivity or capability ranking.
